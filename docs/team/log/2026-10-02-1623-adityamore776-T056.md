- Fuzzed the cross-work builders (the five indexes in `batch.indexes` and the evaluation's `build_store`) with
  damaged rows INSIDE the corpus they read. Realistic faults stopped the Duplicate & Split index or the cohort
  statistics, and so the batch, on every seed: a pandas NaN in a text column, a district code loaded as a number, a

- New `apps/engine/drishti/records.py`: every column the engines read is checked once where the indexes, the
  statistics and the orchestrator take a work (`batch._normalise` uses it too). Text stays as written; a whole

  from date, datetime, ISO text or Indian day-first text; the outside-area flag reads only a clear yes/no. Malformed
  values are dropped, never guessed. A clean row comes back as the same object (no copy of 2 lakh rows).

  `records.day`; `road_curve_rows` skips non-positive amounts and lengths.

## Decisions made (and why)
- Check at the four places a work enters (indexes, statistics, orchestrator, the batch's loader), not inside every
  engine: the engines already survive a bad record alone; the builders did not.
- Text is not trimmed or re-cased: Duplicate & Split compares wording, and a changed answer on clean data would be
  a behaviour change this round did not measure for.
- Day-first text dates ("01/02/2024") read as 1 Feb: eSAKSHI and Indian certificates write day first, and ISO
  text starts with the year, so the two cannot be confused.

## Problems, traps, surprises

  builders had no such guard: they read the whole corpus in one pass, so one row stops them. Fuzz builders with
  damaged rows inside the corpus, not just damaged works assessed against a clean one.
