## Decisions made (and why)
- **The timeline only shows steps with a stored date.** A step that has not happened is left out rather than
  shown greyed or dated "today". The alternative invents history, which is the one thing this site must not do.
- **`entry_id` is outside the hash.** It is the chain's position, not part of what was done, so renumbering
  after a restore cannot be mistaken for a rewritten action.
- **The audit moment is read from the database, then hashed with everything else.** Letting the column
  default to `now()` leaves the time outside the hash, and a row's timestamp could then be rewritten without
  the chain noticing — which is exactly the hole the chain exists to close.
- **Appends are serialised with `pg_advisory_xact_lock`.** Without it two officers acting in the same
  instant read the same `prev_hash` and the chain forks.
- **No setState in an effect.** `useApi` answers "is it loading?" by asking whether the answer on hand
  belongs to the query now on screen, rather than keeping a second piece of state. That is what stops stale
  rows appearing under new filters, and it removed every `react-hooks/set-state-in-effect` error.
- **Resolved without an inspection stays possible** (`NEW/ACKNOWLEDGED → RESOLVED`, note required): the work
  turned out to be recorded already. It just has to say so.
- **`UNABLE_TO_VERIFY` carries no weight**, exactly like `NOT_ASSESSABLE` in an engine. It records that
  nobody could tell, which is not a finding in either direction.

## Problems, traps, surprises
- **React Compiler-era lint rules are strict about effects.** `react-hooks/set-state-in-effect`,
  `react-hooks/refs` and `react-hooks/use-memo` all rejected the obvious "fetch in an effect" shape. The
  fix was better code, not suppressions: one key-derived hook reused by every screen.
- **`[key, path, params]` would have refetched on every render**, because callers pass a fresh params
  object. `[key]` alone is right; the exhaustive-deps warning there is suppressed with the reason written
  next to it.
- **The audit hash must include its own timestamp.** It does not work any other way, and the first version
  of this passed every test except the one that verified the chain — the same class of bug as the regex
  traps in §9 of AGENTS.md: a check that never ran.
- **`psycopg` returns dict rows here**, so `audit.py` uses named columns. Tuple unpacking failed loudly,
  which was lucky.
- **Column controls were showing every column** and could not hide a default-on one. Fixed with an
  explicit shown-list rather than a hidden-list.
- **`SearchBox` keeps its own text**, so the back button does not update it. Not fixed; see next step.

## Not done, and deliberately so
Stated plainly so nobody reads this as T060/T062 finished:
- **T062's actual algorithm is not built.** The spec asks for the greedy value-per-minute planner inside an
  8-hour budget with an OR-Tools TSP and a measured km-saved figure on real districts. This is the visit
  *lifecycle* — request, assign, go out, record, close — which is the shell that planner will sit in. No
  km-saved number exists yet, so none is claimed.
- **T063's field app is partial.** Outcome, free text, recorder and timestamp work; photo capture,
  perceptual-hash reuse, and the "GPS more than 2 km from site → location mismatch" check do not.
- **The hash chain is append-only but not yet tamper-evident against a database owner**, who can rewrite
  the whole chain consistently. Signing each row with a key the site does not hold is the next step up.
- **No digest** (T060's "daily digest to console") and no `POST /plans/generate`.
